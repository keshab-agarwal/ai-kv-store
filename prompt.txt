Task #1:
Build a distributed in-memory key-value store
========================

SPECIFICATIONS:
API: Get/Put/Delete (single-key)
Key: 128-bit RANDOM opaque (treat as bytes[16] / 16-byte string)
Value: max 1 MiB. Typical sizes: mean ≈ 1 KiB
Goal: Latency-focused, state-of-the-art millisecond (ms) latencies
Workload mix: 95% Get / 4% Put / 1% Delete
Capacity: ≥ 1B distinct keys over time
Deployment: Single cluster, Single datacenter (single AZ), Single region

SHARDING & REPLICATION:
The number of shards is specified at cluster startup and is STATIC for the lifetime of the cluster (no resharding).
Each shard has exactly 3 replicas (replication factor = 3) for redundancy.
Shard-replicas SHOULD be placed on different physical nodes to maximize fault isolation (spread across datacenter rack positions where possible). If there are fewer nodes than replicas, co-location is acceptable but must be documented.
Keys are 128-bit random and opaque; you choose the partitioning function to assign keys to shards (hash-based partitioning is natural given the random keyspace, but justify your choice).
Nodes: Range from 3 to 5 nodes in the cluster.

FAULT TOLERANCE:
The system must tolerate exactly 1 fail-stop node failure (crash, no Byzantine faults).
When a node crashes, the surviving replicas of every shard that had a copy on the failed node must continue serving reads and writes with no consistency loss.
Restore full replication (re-replicate under-replicated shards to a recovered or replacement node) within ≤ 30 seconds of the failed node returning.

CONSISTENCY:
Strong consistency (Linearizability, Herlihy–Wing). This KV store is one cluster so does not need to worry about cluster-to-cluster communication.

Definitions:
A history H is the observed concurrent execution trace: a time-ordered sequence of invocation events and response events for operations on the object. An operation is pending in H if its invocation has no matching response later in H. Two events match if they are the invocation/response of the same operation from the same process (same object and process). H' is an extension of H formed by appending zero or more response events to H (to finish some pending operations). complete(H') is the maximal subsequence of H' containing only invocations that have matching responses in H' and those matching responses (equivalently: drop any still-pending invocations). A sequential history S is a single-threaded (non-overlapping) sequence of complete operations (invocation immediately followed by its matching response). S is legal if it satisfies the object's sequential specification (the normal single-threaded semantics). Two histories are equivalent if, for every process, the sequence of operations performed by that process (and their return values) is the same in both histories. Define the real-time precedence relation <_H on operations in H as: a <_H b iff the response of operation a occurs before the invocation of operation b in H. Let <_S be the total order of operations in sequential history S.

Linearizability conditions (must both hold):
L1: complete(H') is equivalent to some legal sequential history S.
L2: <_H ⊆ <_S (if a finishes before b starts in H, then a must appear before b in S).

PERSISTENCE:
Data must be durable. The store is in-memory for the hot path (reads/writes serve from RAM), but all committed writes must be persisted to disk such that:
- A single node crash and restart recovers ALL previously committed data for the shards it owns (from its local persistent state + catch-up from peers if needed).
- A full cluster restart (all nodes stop and restart) recovers all committed data with zero data loss.
You choose the persistence mechanism (WAL, snapshotting, hybrid, or other). Document your choice and its tradeoffs. The persistence path must NOT dominate the latency budget — design it so the common-case write latency remains in the low-millisecond range.

CLIENT LIBRARY:
You must build the client library as part of this task. The client library is how all external callers (benchmarks, test harnesses, applications) interact with the cluster. Design decisions you must make and document:
- Transport protocol (gRPC, raw TCP, UDP, custom, etc.)
- Serialization format (protobuf, flatbuffers, msgpack, custom, etc.)
- How the client discovers which node(s) to talk to (static config, seed nodes, service discovery, etc.)
- How the client routes requests to the correct shard (client-side routing with a partition map, or proxy/coordinator node, etc.)
- Connection pooling and retry strategy
- Timeout semantics and how TIMEOUT is surfaced to the caller
The client library must expose the Get/Put/Delete API specified below. The YCSB binding (Task #2) and correctness harness (Task #3) will use this client library directly — design it to be clean and embeddable.

CONCURRENCY MODEL:
You choose the concurrency model for the server nodes. Document and justify your choice:
- Thread-per-connection, thread pool, event loop (epoll/io_uring), actor model, coroutines/green threads, or hybrid
- How concurrent operations on the same key are serialized within a shard
- How the replication protocol interacts with the concurrency model

PERFORMANCE OPTIMIZATION:
You must optimize the system for the specified workload (95% Get, 4% Put, 1% Delete with Zipfian access). This means:
- The read path should be as fast as physically possible (zero-copy where feasible, minimal lock contention, cache-friendly data structures)
- The write path must satisfy linearizability and persistence requirements but should still target low-millisecond latency
- Network round-trips should be minimized; batch or pipeline replication where safe to do so
- Profile and document where the latency goes (network, serialization, persistence, consensus)
You are expected to make aggressive engineering choices. Justify them.

IMPLEMENTATION LANGUAGE:
You choose the implementation language for the KV store, client library, and any supporting infrastructure. Document your choice and rationale. The only constraint is that the Porcupine linearizability checker (Task #3) must remain in Go (it's a Go library). Everything else is your call.

OUTPUT (from client side):
Put(key, value) → result
Returns OK if the write is committed and persisted.
Returns ERROR if the write fails.
Returns TIMEOUT if the client cannot determine whether the write committed (client may retry).

Get(key) → result
Returns FOUND(value) if the key exists.
Returns NOT_FOUND if the key does not exist.
Returns ERROR or TIMEOUT on failure.

Delete(key) → result
Returns OK if the delete is committed (idempotent: deleting a missing key may still return OK).
Returns ERROR or TIMEOUT on failure.

Custom correctness harness + fault injection + Porcupine linearizability checking

- and verify linearizability using Porcupine (Go library): https://github.com/anishathalye/porcupine

Hard requirements:

A) Node orchestration + fault injection
- Provide a local runner that can start a multi-node cluster (3-node default).
- Must support: start node i, stop node i, crash node i (hard kill), recover node i (restart).
- Crash/recovery must occur DURING the workload run (not only between runs).
- After a crashed node recovers, the harness must verify that re-replication completes and persistence is intact (the recovered node should serve the data it had before the crash, possibly after catch-up from peers).
- Crash schedule must be reproducible via a seed.

B) Workload generator
- Must generate: 95% Get / 4% Put / 1% Delete.
- Keys are 128-bit opaque; values up to configurable max (include a mode that uses realistic sizes up to 1 MiB).
- Must support high concurrency (configurable number of client workers).

C) History format + artifacts
- Must write artifacts to a per-run directory including:
  - a machine-readable history file (e.g., JSONL) with: op_id, client_id, call_time, return_time, op_type, key, input_value, output/status.
  - node logs and harness logs
  - a single summary report (pass/fail + counters + timings)
- The history format must be stable and documented.

D) Porcupine integration (required, must be in Go)
- Provide a Go-based checker tool in-repo that:
  - loads the recorded history,
  - builds Porcupine operations with call/return times,
  - defines a sequential specification/model for the KV semantics (Get/Put/Delete, NOT_FOUND, Delete idempotence),
  - runs the Porcupine linearizability check,
  - outputs PASS/FAIL and writes debug artifacts (e.g., a minimized failing subset and/or visualization if available).
- The harness must run this checker automatically at the end of a test run.

E) Handling TIMEOUT (must be explicitly addressed)
- The harness must not silently ignore TIMEOUT.
- Choose and implement one clear strategy:
  - either retry-with-idempotency so TIMEOUT is rare and operations become determinate for checking, OR
  - record TIMEOUT in a way that preserves correctness checking soundness (explain how the checker treats them).
- Document the chosen strategy and its implications.

F) Self-test / negative control (to prove the checker works)
- Include a built-in self-test mode that:
  - generates a known-good history and confirms Porcupine PASS,
  - then mutates or simulates a known-bad history and confirms Porcupine FAIL.
- This must run without needing the full KV cluster, so the checker pipeline can be validated independently.

G) Exact commands + debugging guide
- Provide exact commands to:
  - start the cluster,
  - run the harness (no faults),
  - run the harness (with 1-node crash + recovery),
  - rerun with same seed for deterministic repro,
  - run the Porcupine checker on a saved history.
- Provide a short guide explaining how to interpret failures and locate the violating operations.

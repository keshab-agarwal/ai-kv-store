Task #1:
Build a distributed in-memory key-value store
========================

SPECIFICATIONS:
API: Get/Put/Delete (single-key)
Key: 128-bit RANDOM opaque (treat as bytes[16] / 16-byte string)
Value: max 1 MiB. Typical sizes: mean ≈ 1 KiB
Goal: Latency-focused, state-of-the-art millisecond (ms) latencies
Workload mix: 95% Get / 4% Put / 1% Delete
Capacity: ≥ 1B distinct keys over time
Deployment: Single cluster, Single datacenter (single AZ), Single region
Nodes: Range from 3 to 5 nodes (each with 2-3 replicas PER node)
Faults: tolerate 1 node crash; restore replication within ≤ 30 seconds
Consistency: Strong consistency (Linearizability)

CONSISTENCY:
Linearizability (Herlihy–Wing) requirement. This KV store is one cluster so does not need to worry about cluster-to-cluster communication.

Definitions:
A history H is the observed concurrent execution trace: a time-ordered sequence of invocation events and response events for operations on the object. An operation is pending in H if its invocation has no matching response later in H. Two events match if they are the invocation/response of the same operation from the same process (same object and process). H' is an extension of H formed by appending zero or more response events to H (to finish some pending operations). complete(H') is the maximal subsequence of H' containing only invocations that have matching responses in H' and those matching responses (equivalently: drop any still-pending invocations). A sequential history S is a single-threaded (non-overlapping) sequence of complete operations (invocation immediately followed by its matching response). S is legal if it satisfies the object’s sequential specification (the normal single-threaded semantics). Two histories are equivalent if, for every process, the sequence of operations performed by that process (and their return values) is the same in both histories. Define the real-time precedence relation <_H on operations in H as: a <_H b iff the response of operation a occurs before the invocation of operation b in H. Let <_S be the total order of operations in sequential history S.

Linearizability conditions (must both hold):
L1: complete(H') is equivalent to some legal sequential history S.
L2: <_H ⊆ <_S (if a finishes before b starts in H, then a must appear before b in S).

OUTPUT (from client side):
Put(key, value) → result
Returns OK if the write is committed.
Returns ERROR if the write fails.
Returns TIMEOUT if the client cannot determine whether the write committed (client may retry).

Get(key) → result
Returns FOUND(value) if the key exists.
Returns NOT_FOUND if the key does not exist.
Returns ERROR or TIMEOUT on failure.

Delete(key) → result
Returns OK if the delete is committed (idempotent: deleting a missing key may still return OK).
Returns ERROR or TIMEOUT on failure.
